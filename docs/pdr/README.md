# Product Decision Records

PDR は Product Decision Record。プロダクト上の選択と理由を、人間と Agent の両方が参照できる形で残す。
大きな設計に限らず、既定値・上限・待機時間・エラー時の体験など、将来コードだけでは理由が分からなくなる判断も対象にする。

人間は [生成された一覧](index.md) から各 Markdown を読める。Agent は一覧の全件読み込みをせず、検索 CLI で候補と必要な章を段階的に取得する。

## 保存と検索

- `records/*.md` が正本。ID は固定し、ファイル名やタイトルを変えても引き継ぐ。
- `.cache/pdr/index.sqlite` はローカルの FTS5 trigram 索引。Git に含めず、欠損・破損時は自動再生成する。
- `index.md` は人間向けに生成するテキスト一覧。直接編集しない。レコード変更後に `pnpm pdr catalog --write` で更新する。
- Node.js 22.22 以上の Node 22 を使用する。SQLite は Node 組み込み機能で、外部サービス・API キーは不要。YAML は `js-yaml` の JSON_SCHEMA で読み、日付も文字列として検証する。

```sh
pnpm pdr search "長文 要約"
pnpm pdr search "8,000 の根拠" --path packages/core/src/runner.ts
pnpm pdr show PDR-20261113-003 --section decision,scope,rationale
pnpm pdr resolve agent.reply.overflow
pnpm pdr history agent.reply.overflow
pnpm pdr context --diff main...HEAD --query "返答の長さ"
pnpm pdr catalog --write
pnpm pdr check
```

`catalog` 以外は JSON を返す。検索の既定は上位 5 件・抜粋 200 文字、本文取得の既定は 80 行。
これは CLI の表示量の初期設定で、プロダクトの返答本文を切る規則ではない。`--limit` / `--chars` / `--lines` で変更できる。
検索は `next_offset`、本文も `next_offset` でページングする。続きは同じコマンドに `--offset` を指定する。
候補の `excerpt_truncated` は抜粋の省略を示す。本文取得でも続きがあることを明示し、黙って内容を切り捨てない。

検索順位はキー・タイトル・用語と識別子・決定本文・全文・対象パスを組み合わせる。
ファイルは加点に使い、除外条件にはしない。`8000` / `8,000` / `8_000` / `8k` と全角表記を正規化する。
日本語の部分一致は trigram と文字列照合を併用し、1〜2文字の検索語も補う。曖昧な同義語は `keywords` に書く。
日本語の自然文は文字種の境界と漢字のまとまりも手掛かりにし、低い重みの2文字の重なりを補助に使う。`approximate:` の一致理由は意味の同一性を保証しないため、本文を確認する。

`authoritative: true` はレコードが `accepted` であるという表示であり、人間承認を CLI が認証したという意味ではない。
検索で関連する提案・未確認記録があれば `attention` も確認する。件数により本文が返っていなくても ID をたどれる。
`resolve` の未決記録も `--limit` / `--offset` で取得し、`attention_total` と `attention_next_offset` を確認する。
`superseded` の本文だけに一致した場合、既定では後継の現行決定へ案内する。過去の本文を調べるときは `search --history` または `history` を使う。
候補と本文の `record_hash` が異なれば、変更後の状態・本文を読み直してから判断する。

索引の指紋には、レコードのパス・全文ハッシュと検索コード・Node の版を含める。
Git の HEAD だけに依存せず、未コミット・未追跡の追加・変更・削除も検知する。各チェックアウト内に索引を置き、一時 DB を構築してから置き換える。
SQLite は候補の全文一致を補助する。メタデータと本文の照合は正本を読み取ったスナップショットを用いるため、索引の順位だけで現行方針を決定しない。

`context --diff` は指定した Git の差分に加え、HEAD からの作業ツリーの変更と未追跡ファイルも対象にする。
新機能でまだ差分がない場合は `search --path` と依頼内容を使う。ルートはコマンドの作業ディレクトリに依存せず、このリポジトリを基準にする。別チェックアウトは `--root` で指定できる。

## 記録するタイミング

1. 依頼内容と変更予定の領域から既存 PDR を検索する。ゼロ件なら用語・識別子・関連パスも変えて探す。
2. 新しい選択が必要なら、[テンプレート](template.md) から `proposed` を作り、選択肢・推奨案・影響を人間へ提示する。依存しない調査は続けてよい。
3. 合意を得たら、判断・理由・範囲を本文で説明し、決定者の識別子を `decided_by` に記録して `accepted` にする。既に明確なユーザー指示がある判断は、同じ承認を取り直さず、決定内容を記録して進める。
4. 実装・レビューでは参照した PDR と、新たに生じた判断を示す。既存方針の変更では後継 PDR と実装を揃える。

人間から許可された作業範囲を、PDR の存在だけで拡張しない。新しい明示指示が過去の PDR と異なる場合は、その変更を示し、新しい指示に従う。
機械的なリネームや挙動を保つ内部整理まで新しい判断・承認を要求しない。
小さな判断は短い記録でよい。PDR 単体で選択・理由・範囲を理解できるように書く。
チャット本文・抜粋・会話ログ・承認リンクは保存しない。判断の理解や正当化に、別の会話や資料を読むことを要求しない。
必要な事実・制約・比較・不利益を本文に要約し、秘密情報・個人情報・無関係な会話を含めない。

## 状態と履歴

| status | 意味 | 現行方針として適用 |
| --- | --- | --- |
| proposed | 人間との議論中 | しない |
| accepted | 人間と合意し、判断と理由を本文に記録した判断 | 範囲・例外を確認して適用 |
| superseded | 後継に置き換えられた判断 | 後継を読む |
| rejected | 採用しなかった案 | 不採用理由を読む |
| unverified | 実装からの観測や、合意・由来が未確認の挙動 | しない |

`key` は論点の固定識別子。一つの key に `accepted` は一件とする。条件別に独立した判断をしたい場合は key を分けるか、一件の範囲・例外に条件を明示する。
意味を変えるときは新しい ID の記録を作り、同じ key と `supersedes: [旧ID]` を設定する。採択時に旧記録を `superseded` にする。
提案中の後継があっても現行の判断を勝手に失効させない。誤字・参照パスの整理と、判断内容の変更を区別する。
採択済みは実装済みを意味しない。実装状況を記す場合は対象の版と確認内容を本文に書き、別ブランチの実装を現在のコードの事実として扱わない。

## メタデータと章

必須は `schema: 1`、固定 `id`、論点 `key`、`status`、文字列の ISO `date`、一つ以上の `areas`。
`keywords` / `paths` / `symbols` は検索の手掛かり。パスはリポジトリからの相対パスで `*` / `**` を使える。改名後も必要なら更新する。
採択済みには `decided_by` が必要。`suzuki3jp` のような決定者の識別子を記録する。
`sources` / `approval` は設けない。承認の証跡やチャットへの参照を要求せず、PDR 本文の説明で判断を完結させる。
日付は `"2026-11-13"` のように引用すると意図が明確になる。ID は現在の例の連番を強制せず、一意で変更されない値を選ぶ。

本文は `# タイトル`、必須の `## 決定` / `## 理由` / `## 範囲と例外` を使う。
必要に応じて `## 選択肢と影響` / `## 未決事項` / `## 再検討条件` を加える。CLI の章名はそれぞれ `decision` / `rationale` / `scope` / `alternatives` / `open` / `revisit`。
理由には解決する課題と選択の妥当性を書く。「指示されたから」やリンクだけで済ませない。小さな判断では一文でもよい。
決定章は結論から書く。検索抜粋だけでは条件が足りないため、実装時は範囲と理由まで読む。

## 人間との合意とレビュー

人間との議論は採択前に行い、合意した結論・理由・適用範囲を PDR 本文へ反映する。会話の原文や承認リンクは持ち込まない。
採択後に判断の意味を変える場合は、人間と改めて合意し、後継 PDR を作る。
`accepted` と `decided_by` は合意状態の記録であり、本人性を認証する仕組みではない。コードレビューの LGTM はプロダクト判断の合意を代替しない。

レビューでは PDR 単体で判断を理解・評価できるか確認する。別資料を読まないと理由や条件が分からない場合は、必要な説明を本文へ補う。
実装中に Agent が追加した値や挙動で合意・理由が不明なものは `unverified` とし、推測で採択済みにしない。
未確認の記録には、何が分かり何が未確認なのかを本文に書く。記録が自己完結していることと、未確認の理由を埋めることは別である。

## 検証

`pnpm pdr check` は書式・必須項目・ID と現行 key の重複・後継関係・循環・ローカルリンクと見出し・生成一覧の鮮度を確認する。
外部 URL の検証は構文のみ。リンク先の存続、人間の本人性、議論と記録の意味の一致、コードとの仕様整合を自動認証するものではない。
`paths` はヒントなので、参照先のコードがこのブランチにまだなくてもエラーにしない。

`pnpm test` に PDR の検証と検索テストを含める。形式に問題がなくても、レビューでは新しい既定値・上限・失敗時の体験が記録と合意を伴っているか確認する。
検索の回帰例には「チャットを保存しない」「長文ならどうする」「なぜ8,000」「通知失敗でRunも失敗するか」「未適用migration」「GIFの背景」「人間承認」を使う。
検索品質は期待する記録が上位に入るか、失効・未確認の判断を採択済みと誤認しないかで確かめる。

形式の参考: [MADR](https://adr.github.io/madr/)。検索機能の参考: [SQLite FTS5](https://www.sqlite.org/fts5.html#the_trigram_tokenizer)。
