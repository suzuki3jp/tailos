# Issue 本文の送信を当面維持し将来は Agent が GitHub から取得する

## 決定

現時点では、Issue のタイトル・本文と受理済み会話を Runner に渡す方式を維持する。PR #57 にはバイト予算による履歴省略や、最新計画による Issue タイトル・本文の自動編集を追加しない。

将来の Runner 入力は、Issue 本文を事前に展開して渡す方式から、対象 Issue の番号をコンテキストとして渡し、Agent が GitHub に問い合わせてタイトル・本文など必要な情報を取得する方式へ移行する。Issue 番号は対象リポジトリの実行コンテキストと組み合わせて解決する。

## 理由

API が Issue 本文や履歴をジョブへ詰め込む方式では、取得する情報が増えるたびに入力構築とジョブ契約への影響が大きくなり、Runner HTTP のサイズ上限にも依存する。対象の識別情報を渡し、Agent が必要な情報を GitHub から取得する方式は、調査対象や参照情報の追加に対応しやすい。

その方向へ移行する予定のため、今回は暫定的な履歴選別や Issue 本文の管理方式を追加せず、現行実装を維持する。

## 範囲と例外

採択したのは当面の現状維持と将来の取得方式の方向性であり、この記録によって移行を実装済みとは扱わない。今回の作業は PDR の記録に限定する。

移行までの計画会話には [PDR-20261113-012](PDR-20261113-012.md) を適用する。最終ジョブ全体の UTF-8 サイズが 32 KiB を超えると `planning_input_too_large` で失敗し、保存済み入力は残る。履歴の蓄積で継続できなくなる制約も当面残る。

## 未決事項

将来の入力契約、取得した情報のスナップショットと追跡方法、受理済み指示と参照用コメントの区別、取得量・ページング・取得失敗時の扱いは移行時に設計する。GitHub から取得する方式にすることだけでは、これらの挙動や上限を決定したことにはならない。
