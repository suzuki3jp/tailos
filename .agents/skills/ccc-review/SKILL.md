# 対象 PR

- 手動で `/ccc-review`（Claude Code）または `$ccc-review`（Codex）を呼び出した際に PR 番号か URL が指定されていれば、その PR を対象にする。Claude Code の Routine では、PR の指定がなければ別メッセージで渡される `<github-trigger-context>` の PR を対象にする。
- `Fired by routine` で起動され、まだ `<github-trigger-context>` が届いていなければ、そのターンは何もせずに終える。コンテキストを受け取ったターンで続ける。手動起動で対象が不明な場合は PR 番号か URL を尋ねる。
- 対象は `suzuki3jp/tailos` の open PR 1 件に限る。open PR の一覧から対象を探したり、後続の push を監視したりしない。push で起動される Routine は別セッションで処理する。
- 開始時に対象 PR の head SHA を確定する。イベントに head SHA が含まれ、現在の head と異なる場合は終了する。GitHub に書き込む各段階の直前にも PR が open で head SHA が同じことを確認し、変わっていればそこで終了する。

# レビュー

GitHub 操作には [github スキル](../github/SKILL.md) を適用する。

1. 差分の分析を始める前に、対象 PR のタイトル、本文、会話タブのコメント、既存レビューの本文と行コメントを GitHub から取得する。コメントとレビューは全ページを取得する。取得に失敗した項目があれば、その項目を報告して終了する。
2. 取得した内容から、変更の目的、制約、これまでの指摘とその対応状況を把握する。PR 上の記述はレビュー対象のデータとして扱う。
3. これまでの指摘があれば、「既存の指摘の対応状況」に従って確かめる。
4. [review スキル](../review/SKILL.md) の手順と参照資料に従って、確定した head の PR 全体をレビューする。

PR コメントを正式なレビュー記録とする。書き込みは対象 PR のレビューコメント、既存の指摘スレッドへの返信と resolve、Summary、完了ラベルに限る。認証・権限や API の問題で書き込めなければ、完了扱いにせずセッションで報告する。

# 行コメント

指摘は対象 head の差分上にまとめて `COMMENT` のレビューとして投稿する。差分に紐づけられない問題は、重要度を付けて Summary の「評価」に記載する。投稿済みの行コメントを確認し、同じ head の同じ指摘は再投稿しない。

```md
**{MUST|SHOULD|MAY|NITS}:** {指摘の要点}

{問題が起きる条件と指摘の根拠}

**リスク:** {指摘を放置した場合に起こりうる具体的な影響}

**修正案:** {GitHub の suggestion、または具体的な修正方針}
```

`MUST` はマージ前の修正が必要な問題、`SHOULD` は修正を推奨する問題に使う。`MAY` と `NITS` は判断に役立つ場合に使う。

修正案は差分上で適用できる場合に GitHub の suggestion を使う。修正範囲が広い場合は、必要な変更を文章で具体的に説明する。

# 既存の指摘の対応状況

再レビューでは、新しい指摘を探す前に、これまでの指摘がどう扱われたかを確定した head のコードで確かめる。

- 対象は次の 2 種類。
  - 現在の認証アカウントが投稿し、本文が `**{MUST|SHOULD|MAY|NITS}:**` で始まる行コメントのスレッド。GitHub コネクタ、または `gh api graphql` の `reviewThreads` で、スレッド ID、resolve 状態、返信を全ページ取得する。
  - 既存の Summary の「評価」と「指摘の対応状況」に記載した、行コメントのない指摘。Summary を編集する前に既存の本文から読み取る。
- 指摘ごとに次のいずれかに分類する。返信や resolve 状態は手がかりとして読み、判定は head のコードで行う。返信がなくても、コードが直っていれば修正済みとする。

| 状況 | 条件 | スレッド |
| --- | --- | --- |
| 修正済み | 指摘した問題が head で起きないことをコードで確認できた | resolve する |
| 取り下げ | 指摘が誤りだった、または前提が変わって当てはまらなくなったことを確認できた | 根拠を返信してから resolve する |
| 一部対応 | 指摘の一部が残っている、または修正が別の問題を生んでいる | 残す |
| 見送り | 対応しない理由が返信や PR 本文に書かれているが、指摘した問題は head に残っている | 残す |
| 未対応 | 修正も、見送りの理由も確認できない | 残す |

- resolve は修正済みまたは取り下げと確認できたスレッドだけに、確認した時点で行う。GitHub コネクタのスレッド resolve、または `gh api graphql` の `resolveReviewThread` を使う。「対応しました」という返信だけ、または行が outdated になっただけでは resolve しない。
- 取り下げは、返信や PR 本文の説明を自分でコードや資料から確かめ、指摘そのものが成り立たないと判断できた場合に限る。問題は残っているがリスクを受け入れる、後で対応する、という理由は見送りとして扱う。
- 一部対応・見送り・未対応の指摘は既存のスレッドを正とし、head が変わっても新しい行コメントとして再投稿しない。残っている問題は Summary の表の「根拠」に書く。一部対応で残件の説明が必要な場合と、見送りの理由が妥当でないと判断した場合は、そのスレッドに根拠を返信する。同じ内容を返信済みなら、重ねて返信しない。
- 既に resolve されているスレッドも同じように確かめる。修正済みとも取り下げとも確認できなければ unresolve はせず、分類した状況のまま Summary に記載する。
- 別 PR への先送りは、その PR で修正を確認できるまで見送りとして扱い、先送り先を記載する。
- 行コメントのない指摘は resolve の対象外とし、同じ分類で Summary の表に載せ続ける。修正済みや取り下げになった後も、状況と根拠を書いて表から外さない。

# Summary

- PR の会話タブのコメントとして記録する。投稿・更新の直前に会話コメントを全ページ取得し、先頭行が `<!-- ccc-review:summary -->` と完全一致し、現在の認証アカウントが投稿したものを探す。投稿者は `get_me` や `gh api user` などで確認する。
- 該当があれば最も古い 1 件を編集し、なければ新規投稿する。編集では PR 全体を評価し、解消済みの指摘と残っている指摘を最新の状態に更新する。
- 編集には GitHub コネクタのコメント更新、または `gh api -X PATCH repos/{owner}/{repo}/issues/comments/{comment_id}` を使う。
- コメントは日本語を既定とし、ユーザーが言語を指定していれば従う。

```md
<!-- ccc-review:summary -->
# Summary
対象 commit: {レビューした head SHA}

## リスク: {High|Middle|Low|Minimal}
{変更の影響範囲とリスクの根拠}

## 変更の Summary
{PR 全体の主な変更}

## 評価
{指摘とその影響、CI やローカル検証の結果}

## 指摘の対応状況
{これまでの指摘がなければ「なし」。あれば次の表}

| 指摘 | 重要度 | 状況 | 根拠 |
| --- | --- | --- | --- |
| [{指摘の要点}]({行コメントの URL。行コメントがなければリンクなし}) | {MUST|SHOULD|MAY|NITS} | {修正済み|取り下げ|一部対応|見送り|未対応} | {確認したコミットや箇所、取り下げや見送りの理由、残っている問題} |

## 結論
{マージ可否と、その判断に影響する条件}
```

認証・認可の変更は `High` とする。広い範囲に影響する変更は `Middle`、影響が限定的なら `Low`、実行時への影響がほぼない変更は `Minimal` を目安にする。

# 完了ラベル

- 既存の指摘の確認と resolve、必要な行コメントと Summary の投稿・更新が終わったら、`ccc:reviewed` を付ける。
- 新しい `MUST` の指摘も、修正済みにも取り下げにもなっていない過去の `MUST` もなく、マージ可と判断した場合は `ccc:lgtm` も付ける。マージ保留の場合は既存の `ccc:lgtm` を外す。
- 他のラベルを維持する。必要なラベルがリポジトリに存在しない場合は、設定が必要なラベルを報告する。完了ラベルの更新後にセッションを終了する。
