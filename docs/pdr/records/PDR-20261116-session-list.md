# アカウントのセッション一覧に起動元と会話の要約タイトルを表示する

## 決定

アカウントホームで現在のアカウントの会話一覧を表示し、選んだ会話から Session のチャット画面へ移動できるようにする。そのための一覧 API、起動元の参照情報、会話タイトルの方針を採択する。

### 一覧 API

- API サービスに `GET /api/sessions` を追加する。Web は既存の API クライアントと同様に API サービスを直接呼ぶ。`/api` は既存のブラウザー向け API が使うプレフィックスである。
- 既存の運用者認証を使い、認証結果のユーザー ID と `sessions.owner_id` が一致する行だけを返す。取得対象の所有者をリクエストから指定する機能は設けない。
- 並び順は `updated_at DESC, id DESC` とし、更新日時が同じ行にも一意の順序を与える。ページングを提供する。
- 一覧に Session ID、タイトル、起動元、Project の識別情報、作成日時、更新日時を含める。JSON のプロパティ名は既存の契約に合わせて camelCase とする。
- `updated_at` の更新契機と理由は [Session の更新日時の判断](PDR-20261116-session-updated-at.md) に従う。

### 起動元

`Triggered by Issue #33` と表示し、対象 Issue を識別・参照できる情報を返す。GitHub 起点の `trigger` は次の構造とする。

```json
{
  "kind": "github.issue",
  "repository": "owner/repo",
  "number": 33,
  "url": "https://github.com/owner/repo/issues/33"
}
```

repository を含め、異なるリポジトリの同じ Issue 番号を区別する。起動元は API 側の保存データから返す。ラベル・コメントの違いを表示することは必須要件としない。

### タイトル

- GitHub 起点の初期タイトルには Issue タイトルを使う。
- 最初の正常な Agent 応答で、会話の目的・内容を簡潔に要約したタイトルへ一度だけ置き換える。その後の会話では自動変更しない。
- Agent が失敗した場合は初期タイトルを維持し、次の正常応答で置き換えを試みる。
- タイトルだけが不正・取得不能な場合も初期タイトルを維持する。タイトルだけの不備を理由に、本来の返答や実装成果を失敗扱いにしない。正常なタイトルが得られるまでは、後続の正常応答で置き換えを試みる。
- タイトルは Agent の正常な応答を受理・保存した時点で反映する。PR 公開まで含む Run 全体の成功は待たない。

### 構造化応答

既存の最終応答の JSON Schema に `sessionTitle` を追加する。計画用の `reply`・`planPresented`・`needsAnswer`、実装用の `reply`・`headline` と同じ応答で取得する。会話タイトルとコミット用の `headline` は別の値として扱う。タイトル専用の追加 Agent 呼び出しは行わない。

Codex・Claude の両方で既存の構造化応答の経路を拡張する。形式をランタイムの JSON Schema で指定し、タイトルは Runner でも検証する。タイトルの意味・品質はスキーマだけでは保証できないため、会話の目的・内容を簡潔に要約する指示も与える。

構造化応答に関するこの判断は、タイトル以外の応答が不正な場合に既存の検証を省略するものではない。

## 理由

既存の HTTP API は所有者に限定した Session 詳細取得を提供するが、一覧取得を提供していない。会話一覧にタイトルと対象 Issue を識別できる起動元があれば、利用者が開く会話を選びやすい。起動イベントの種類だけでは `Issue #33` を表示できないため、repository・Issue 番号・リンクを返す。

更新日時順なら最近活動した会話を見つけやすい。Run の失敗には返信メッセージを伴わない場合があるため、メッセージ追加だけでなく Run の状態遷移も更新対象とする。返信のない失敗にも気づけることが、この判断の理由である。

Issue タイトルを初期値にすると Agent の返答前にも一覧を表示できる。Agent の最初の応答と一緒に要約タイトルを取得すれば、会話の実際の内容に合うタイトルへ置き換えられ、タイトル専用の待ち時間や呼び出しも増えない。一度だけ置き換えることで、以後の会話で名前が変わり続けることを避ける。

Agent の失敗やタイトルだけの不備で会話名を失ったり、本来の処理を失敗させたりしないよう、初期タイトルを残す。最初の正常応答を待つ方式なら初回失敗後もタイトルを生成できる。Agent 応答と PR 公開は別の段階なので、公開結果に関係なく保存できた応答の内容をタイトルへ反映する。

件数を区切って取得すると、会話数が増えても一回の取得量を制御できる。更新日時と ID の組で順序を定めることで、同時刻の行をページ境界で区別できる。

## 範囲と例外

対象は会話を表す `sessions` であり、ログイン状態の一覧ではない。所有者が一致すれば Project の有無に関わらず対象にする。削除済み Project の過去の Session も所有者が閲覧できる既存方針を維持する。

この PDR は仕様の採択を記録する。API・Runner・Web の実装完了を意味しない。Web ホームのプレビューを実データへ接続する作業は別途行う。MCP の一覧の並び順や既存のカーソル契約は今回の採択対象に含めない。

起動元を Agent に生成させない。タイトル生成のために Runner へ渡す Issue 本文を増やす必要はなく、既存の Issue 取得・内容ハッシュ照合を維持する。返答本文が上限を超えた場合の要約方針も維持する。

PR 公開や復旧経路でも受理済みのタイトルを失わないようにする。タイトルなしの結果を返す既存 Runner イメージとの互換性を保ち、タイトルがないことだけで既存の処理を失敗させない。

## 選択肢と影響

- Issue タイトルだけで固定する方式は単純だが、会話内容を要約したタイトルへ置き換える用途を満たさない。
- 毎ターンのタイトル更新は最新の内容を反映できるが、一覧で覚えた会話名が変わり続ける。一度の置き換えを採用する。
- タイトル専用の Agent 呼び出しは処理と待ち時間が増えるため、既存の応答へフィールドを追加する。
- 初回失敗でタイトル生成を諦める方式では、再開後も初期タイトルのままになる。正常な応答・タイトルが得られるまで置き換えの機会を残す。

## 未決事項

以下は本記録の採択時点では確定していなかった。後続の採択済み判断で、ページング・取得中の更新・レスポンス項目は [一覧 API の契約](PDR-20261116-session-list-contract.md)、タイトルの検証・確定・公開復旧は [生成タイトルの検証と保存](PDR-20261116-session-title-validation.md)、初期値・既存データの補完・計画 inbox は [メタデータの補完](PDR-20261116-session-metadata-backfill.md) に確定内容を記録した。以下の一覧は採択時点の論点として残す。

- ページングの具体的なリクエスト・レスポンス形式、既定件数、最大件数、不正なパラメーターへの応答。既存案の `{ items, nextCursor }`、カーソル方式、既定 50 件・最大 100 件は候補である。
- 取得中の更新で行がページ間を移動する場合の扱い。ページ間でスナップショットを固定せず、先頭の再取得で最新状態を反映する方式は候補である。
- まだメッセージや Run に割り当てていない計画 inbox の入力受理も更新対象に含めるか。
- 生成タイトルの長さ・言語・空白の扱いと、タイトルだけの不備を切り離せる具体的なスキーマ・検証方法。
- 既存データの初期タイトル・起動元・更新日時の補完と、情報が不足する場合の扱い。保存されていない過去の状態遷移時刻を正確に復元できるとは扱わない。
- GitHub 以外の初期タイトル・起動元と、初回以外の別 Issue の関連付けが生じた場合の扱い。
- 一覧に本文プレビューや `latestRun: { id, status, errorCode } | null` も含めるか。更新日時だけでは失敗したこと自体の表示はできないため、最新 Run の状態を返す案を検討する。
- 要約タイトルの一度だけの確定を原子的・冪等に行う保存方法と、公開・復旧経路で受理済みタイトルを引き継ぐ具体的な実装。
