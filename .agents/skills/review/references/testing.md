# Testing

## テストの実行方法

```sh
pnpm test
```

ルートから各 workspace のテストを実行する。テストが対象のパッケージや実行経路をカバーしているか確認する。

## テストするかどうかの判断基準

以下の場合にテストの必要性を検討する。

1. 対象のコードが複雑である場合
2. 対象のコードにバグが含まれていたときの影響が大きい場合
3. 対象のコードが純粋で、単純なユニットテストで挙動を確かめられる場合

Run の進行、Webhook、PR 作成を変更する場合は、重複配送、同時実行、途中で失敗した操作の再試行のうち、変更に関わるケースを確認する。

## テストを書く際のポイント

- テストは変更を検出するために書くのではなく、仕様を実装できているかを検出するために書くべきである。つまり、実装を変更するたびにテストを変更するようなテストはかかずに、仕様が検証されている状態を維持する。
- モックは最低限にする。Agent 実行を固定応答の Adapter に置き換えても、今回確認したい API や永続化の境界は通す。
- テストの対象はできるだけ小さくし、名前は英語で付ける。
- 正常系に加えて、影響のある異常系や境界値を確認する。

## いいテストとは

- 失敗したときに、どの振る舞いに問題があるかが分かる。
- 実行順序やタイミングに左右されず、安定している。
- 純粋な関数にはユニットテストを使い、複数のコンポーネント間の契約や復旧処理には必要な境界を通るテストを使う。
