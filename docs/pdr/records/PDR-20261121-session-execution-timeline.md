# セッション向けの実行タイムラインを保存し実行中も配信する

## 決定

実行中の進捗とツール呼び出し、完了後の閲覧を同じタイムラインの契約で扱う。diagnostics の Trace・Span をブラウザで組み立てる代わりに、Session が読む実行 Item のモデルを設ける。Run の成否と最終回答は既存の業務ストアを正本とする。

Codex / Claude の Adapter で通知を共通の実行イベントへ変換する。プロバイダの raw RPC や SDK の型を API・Web の契約にしない。同じ検証済みの観測からタイムラインと診断を作り、秘密情報除去、配送の再送、Artifact の保存などの部品を共有する。同じ本文を保存するときは参照を共有し、別々の秘匿処理や同じイベントの二重計測を避ける。

Item は Agent の進捗メッセージ、最終回答候補、コマンド、Web 検索、MCP / dynamic tool、ファイル変更、実行段階を表す。開始・完了・失敗・中断・結果不明を区別する。内部の推論は収集しない。実行段階は checkout、Agent、公開、cleanup など実際に観測できるものを表示し、根拠のない完了率を作らない。

永続化は D1 の実行イベントと表示用 Item、非公開 R2 の大きな本文を基本とする。短い検査済みの進捗本文やラベルは Item に含め、初期表示のために R2 の全本文を取得しない。診断 Event は保守用、実行 Item は利用者向けの読み取りモデルであり、既存の会話メッセージへすべてのツールログを追加する設計にはしない。これらを Agent へ渡す会話履歴に自動で含めない。

### 段階的な配信

最初の段階でも、実行中に短い進捗メッセージを表示し、コマンドやツールは開始直後に表示して完了時に状態と結果を更新する。進捗メッセージは一つのメッセージが完成し、検査を終えた時点で配信する。ツールの名前・コマンド・引数も検査対象である。長いコマンドの出力は完成時に検査して保存・表示する。この段階はイベントのライブ配信であり、本文の文字単位の streaming は提供しない。

Agent に短い進捗を返すよう促す場合も、実際に通知された本文だけを表示する。heartbeat は接続状態、無出力の実行は実行状態として扱い、モデルが報告した進捗と混ぜない。

後続の段階で本文の delta 配信を加える。既知の秘密値が断片に分かれる場合、複数行の秘密鍵、UTF-8 の文字境界を扱う状態付きの検査が前提となる。固定長の末尾保留や、各時点の累積本文の再検査だけで安全とはみなさない。後続文字から初めて秘密と判明する接頭辞は既に表示済みになりうる。安全な確定境界を定義できない内容は完成まで保留し、検査失敗時には本文を配信しない。検査対象・保証・省略規則は、この段階の実装に先立って別途合意する。

現在の Codex Adapter は `item/started` / `item/completed` の一部を処理する。delta 配信には `item/agentMessage/delta`、`item/commandExecution/outputDelta` などの追加処理が必要である。[Codex app-server の公開ドキュメント](https://developers.openai.com/codex/app-server)にはこれらが記載されるが、Dockerfile が固定する Codex `0.166.0` の `app-server generate-json-schema` で、`item/started` / `item/completed`、`agentMessage.phase` の commentary / partial_answer / final_answer、および command / tool の Item を確認した。実モデルを伴う本番での通知頻度は未計測である。phase が null または未知の種類なら推測で進捗に分類しない。[Claude Agent SDK の増分出力](https://platform.claude.com/docs/en/agent-sdk/streaming-output)も Adapter 内で正規化する。

### 最終回答との整合性

`runAgentTurns` は Run により JSON の構造化出力を要求し、長い回答を同じ thread の後続 turn で短縮する。`agentMessage` の全テキストをそのまま会話の回答として追加しない。commentary と最終回答候補を phase・turn・revision で区別し、JSON の制御項目や短縮前の回答を通常の最終回答として確定しない。phase を取得できない版では推測で分類しない。

最初の段階では構造化された最終回答の raw delta を表示せず、検証済みの `reply` を既存の Session メッセージとして確定する。後続段階で回答本文も逐次表示する場合は、JSON の `reply` の増分デコードと秘匿処理を行い、最終的には業務ストアに保存された回答へ置き換える。Item と Session メッセージを Run・turn・Item の対応で結び、回答を重複表示しない。

Agent の turn 完了と Run の完了は区別する。最終回答候補があっても公開処理が残る間は「公開中」等を表示する。確定した Run の結果を配信するのは業務更新後とする。

### 履歴と整合性

配送は既存の version / eventId / producerId / seq / spanId / at を利用し、Run と Session は検証済みの ingest 先から解決する。spanId から安定した Item ID を作り、保存側で cursor を割り当てる。プロバイダの turn ID は初期の表示契約へ露出させず、進捗と最終回答は検証済み phase と既存の回答確定経路で分離する。受信側で所有者と Run・producer を照合する。重複は `eventId` と producer の順序で検出し、同じ ID の異なる内容を拒否する。表示 Item の更新にも単調な revision を設ける。

再開カーソルはクライアント時刻や producer の最大 seq ではなく、Session 内の保存済み受信順を使う。遅れて到着したイベントも取得対象になる。Item 内の出力順は producer の順序・出力 offset で検証する。欠落を飛ばして連結したり、遅延した開始通知で完了済み Item を実行中に戻したりしない。

ACK とライブ配信は保存コミット後とする。R2 本文を使う場合は先に R2 へ保存し、D1 のイベント・Item・本文参照を同じ batch で確定する。R2 と D1 の横断トランザクションは仮定しない。ACK 消失時の同一バッチ再送を受理できるようにし、保存後の通知失敗は永続的な通知待ち記録から再試行する。画面は受信済みカーソルから再取得できる。

詳細なタイムラインの記録失敗だけで業務結果を失敗へ変えない。保存上限、配送失敗、検査失敗、未完了 Item、失効を UI で区別する。Run の成功からログの完全性を推測しない。最終位置と欠落件数を別に持ち、コンテナ消失時も取得済み履歴を保持する。未完了の処理を成功として閉じない。

## 理由

PR #112 の head `7615dc3` は、Project 内の会話と保存済み Agent 実行時間、一覧の並列 prefetch を提供している。実行中の詳細は 5 秒ごとの Session 取得で更新する。`RunActivity` のクリックは矢印の回転のみであり、ログ本文の取得や展開を実装していない。

diagnostics は Runner から 1.5 秒間隔で送信し、完成した本文を検査して R2 に保存する。文字単位の delta は収集しない。既存取得 API を画面から使うと Trace、Event のページ、Artifact のバッチ本文を取得して再構成する必要があり、単に polling を WebSocket に替えても、進捗の粒度と初期取得の依存関係は改善しない。

利用者向けの Item を持つと、コマンドや検索を一つのまとまりとして更新でき、保存済み表示とライブ表示が同じ renderer を使える。既存診断の payload や保持契約の都合を UI の公開 API に直接持ち込まずに済む。一方で、新しい保存契約、読み取りモデルと欠落状態の保守が必要になる。

## 範囲と例外

最初の実装は、完成した進捗メッセージとツールの開始・完了のライブ配信、および保存済み履歴の表示を対象とする。セッション画面の後継判断と合わせて実装する。文字単位の delta 配信と Agent の中断・追加指示は後続段階である。

既存の所有者認証と保存済み Project ID の一致を、初期取得、履歴、本文取得、購読の全経路で確認する。削除済み Project の履歴閲覧は既存方針を維持する。任意の R2 key を外部から指定させない。本文を公開 CDN や別ユーザーと共有するキャッシュへ置かない。

本文の保持は診断と同じ本文 30 日、経路・メタデータ 90 日とし、最終回答は既存 Session の保持に従う。D1 に含める短い本文にも同じ失効・削除を適用する。このため完了後も見られるが、ツール本文を Session の寿命全体にわたって保証する案ではない。長期保持の必要性は未確定である。本文の失効と未収集を区別し、診断本文を参照する場合はその期限より長く表示できると約束しない。

128 KiB の本文上限、Run あたり 32 MiB / 10,000 Event など既存の保護を起点として容量設計を行う。新契約に無検討で同数を追加したり、token ごとに Event を消費したりしない。予算の共有と課金対象の計算は実装前に具体化する。高頻度更新はまとめ、最終 Item と検査済み出力を保存すれば過去表示できる設計とし、文字の出現順をアニメーションとして完全再生することは要求しない。

既存 Run の過去の delta や未収集メッセージは復元できない。保存済み診断から変換できる項目だけを表示し、完全性と元の保存期限を引き継ぐ。

診断や token 更新だけで Session の一覧順を変えない [PDR-20261116-session-updated-at](PDR-20261116-session-updated-at.md)、記録失敗で業務結果を変えない [PDR-20261119-runner-failure-diagnostics](PDR-20261119-runner-failure-diagnostics.md)、返答の短縮に関する [PDR-20261113-003](PDR-20261113-003.md) を維持する。数値や失敗時の補助挙動が未確認の PDR は採択済みの根拠にしない。

## 選択肢と影響

| 方法 | 利点 | 不利益・適する条件 |
| --- | --- | --- |
| diagnostics を拡張し、その保存モデルから直接読む | 既存の認証・秘匿・再送・容量管理を多く使える。変更を小さくしやすい | Span の結合、本文の追加取得、best effort と保存期限を UI が引き受ける。delta を追加するだけではイベント上限と秘匿の前提を壊す。短期の診断表示には向く |
| Session 向け実行 Item とイベントを追加し、診断の基盤を共有する（推奨） | メッセージ・ツールの意味を安定した API とし、履歴とライブを共通化できる。初期取得を最適化できる | 新しい契約と投影の整合性が必要。D1 の書き込み量に注意し、失敗・保持の扱いを定める必要がある |
| Session ごとの Durable Object SQLite を実行履歴の正本にする | 順序付け、履歴とライブの整合性、高頻度書き込みを Session 内に集約できる | D1 の所有者・Run 状態と保存先が分かれ、削除・清掃・移行・検索・確定通知の調整が増える。頻度や規模が D1 案の制約になるときの有力案 |
| Codex app-server を直接ブラウザへ公開する | Codex の通知を比較的そのまま利用できる | 認証 RPC・秘密値・制御権を露出させる危険があり、固定版や Codex 固有のモデルに依存する。現在は ephemeral thread と破棄されるコンテナなので永続履歴も別途必要。採用しない案 |

## 未決事項

- 本文保持を 30 日とする案が十分か。長期保持が必要ならコピー先・削除と費用を含めて決める。
- 初期取得と追加取得は 100 Item、短い本文は JSON エスケープ後の UTF-8 で 8 KiB 以下とする。超える本文は省略・切断せず R2 参照から展開時に読む。運用での読み取り量と負荷を確認する。
- 固定版のプロバイダ通知で commentary と構造化回答を識別できる範囲。進捗文の生成をどの指示に追加するか。
- delta 配信に必要な状態付き秘匿検査の仕様、保証できない内容の保留・省略とユーザーへの表示。
- D1 への書き込み負荷を実測した結果、最初から DO SQLite を正本にする必要があるか。

## 再検討条件

高頻度出力や同時実行数によって D1 の書き込みが業務更新を遅らせる場合、Session 単位の DO SQLite または診断と分離したストアへ移す。初期実装で token 単位の D1 / R2 書き込みを行わない。
