# Issue の明示コマンドで計画会話を永続化する

## 決定

open な Issue の新規コメント先頭の `@tailos plan` で計画を開始する。同じ Issue の以後の `@tailos <回答・修正依頼>` と再度の plan は同じ Session の計画更新になる。実装ラベルは不要とし、コメントから実装・PR 作成へ進めない。開始前の回答には開始方法を案内する。メンションのない投稿、引用・コードフェンス中のコマンド、編集・削除、Bot、PR、closed Issue、許可外の主体を起動対象にしない。

owner、project、repository ID、Issue 番号で会話を分離する。受理したコメントは永続 inbox に保存し、永続化順で一つずつ Run に割り当てる。delivery と comment ID の双方で重複排除する。D1 を会話の正本とし、Run 開始時の Issue タイトル・本文・基準 SHA と対象入力・会話を保存する。最新の成功計画と最新の試行を別に識別し、質問だけの結果や失敗後に古い計画を最新として扱わない。

計画・質問の文章返信は画像の状態通知と別に保存する。成功・失敗結果と返信待ちを原子的に保存し、会話順で送信する。投稿不明時は Run・入力・通知種別のマーカーと App 投稿者を照合して全ページから回収する。恒久失敗は診断を残して後続返信を解放し、返信失敗で Agent を再実行しない。

## 理由

実行中の追加指示を既存 Run にまとめるだけでは本文が失われる。会話と入力割当を永続化すると、同時受付や Worker 停止後も受理した依頼と結果を追跡できる。実行と通知を分離すると GitHub の障害から返信だけを回収できる。質問を正常終了として保存することで、人の回答待ちにコンテナを保持する必要がなくなる。

## 範囲と例外

Issue #52 の依頼で明示された会話仕様に適用する。既存 PROJECTS、installation、allowedActors、運用者の Codex 接続と Session アクセス制御を再利用する。GitHub の任意コメントは会話へ取り込まない。ラベルから計画を実装に引き継ぐ操作は別の実装範囲である。

入力の切り捨ては行わず、共有の prompt 上限 4,000 文字を維持した固定指示と、別フィールドの構造化スナップショット・会話を渡す。既存 Runner HTTP の 32 KiB 上限を最終ジョブの UTF-8 バイト数で検証する。上限超過は保存済み入力を残して `planning_input_too_large` で終了し、取得・保存の失敗も失敗結果と返信で追えるようにする。長い会話を無制限に再開できる仕様ではない。返答 8,000 文字の上限と意味を保持する要約方針は既存の契約を維持する。
