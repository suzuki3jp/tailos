# Issue の参照情報と内容ハッシュを渡し Agent が GitHub から取得する

## 決定

PR #57 の後続で、GitHub Issue を起点とする計画・実装ジョブは、タイトル・本文を開始プロンプトに埋め込む方式から、構造化した `githubContext: { kind: "issue", number, contentHash }` を Runner に渡す方式へ移行する。Agent は対象リポジトリに制限された `tailos_github_get` を自分で呼び、Issue のタイトル・本文を取得して作業する。

新しい実装ラベル受付では、許可された投稿者がラベルを付けた Webhook に含まれるタイトル・本文の SHA-256 を実行コンテキストへ保存する。Runner は最初の GitHub 取得時に照合し、不一致の本文を指示として Agent に返さない。計画ジョブも保存済みの開始前スナップショットのハッシュを照合する。本文をジョブへ含めず、起動時に確定した内容と実行対象を結びつける。

新しいラベル受付のプロンプトは固定の作業指示だけにする。計画ジョブは開始前の Issue スナップショットを D1 に保存し続けるが、Runner に渡す `planningContext` にはタイトル・本文を含めず、基準 SHA と受理済み会話を渡す。

対象 Issue の本文を取得しきらずに Agent が終了した場合は、成功扱いにせず既存の `agent_failed` とする。取得失敗は同じ実行中に再試行できる。ツールの既存の本文上限 16,000 UTF-16 単位を一回の取得量として維持し、`bodyOffset` / `nextBodyOffset` で残りを取得できるようにする。サロゲートペアは分割しない。対象 Issue は最初に取得した結果を実行中に保持し、ページ間で編集された本文を混在させない。

## 理由

Issue の内容をジョブへ事前展開すると、参照情報の追加が API のプロンプト構築やジョブのサイズ上限に結びつく。識別情報を渡して Agent が取得する方式は、参照対象を増やしやすく、長い Issue 本文も小さいジョブで扱える。取得したかどうかと全文の取得範囲を確認すると、参照漏れや先頭ページだけに基づく成功を防げる。ラベル付与後に作成者が本文を編集できるため、本文の照合なしでは許可された利用者が起動した内容と異なる指示を実行する可能性がある。ハッシュの照合は本文をジョブから除く方針と、従来の内容の固定を両立する。

## 範囲と例外

[PDR-20261114-003](PDR-20261114-003.md) の取得方式に、従来の起動内容との結び付きを保持する照合を加える。[PDR-20261113-012](PDR-20261113-012.md) のうち Issue タイトル・本文を Agent に事前送信する部分には本記録を適用し、会話の受付順・保存・通知とモードの制約は維持する。受理済み会話は引き続き D1 を正とし、任意の GitHub コメントを自動で指示に取り込まない。Issue のタイトル・本文は自動編集しない。

ラベル付与者の権限は起動時に検証し、そのイベントの本文ハッシュで内容も結びつける。計画ジョブでは開始前スナップショットに結びつける。取得前にタイトル・本文が変わっていれば照合に失敗し、元の内容へ戻らない限り同じ Run では使用できない。新しいラベル受付または計画入力で改めて開始できる。ハッシュは `JSON.stringify([title, body ?? ""])` の UTF-8 バイト列に対して計算し、null と空の本文は同じ内容として扱う。診断が有効な場合はツールの入力・応答を既存の診断経路に記録する。

`githubContext` は新しいジョブで使用する任意フィールドとし、これを持たない既存ジョブは従来どおり処理できるようにする。Tailos は `durable_object` scheduling policy と名前付きイメージを使い、Run ID ごとの DO がその Worker バージョンの `ctx.container.images.runner` を明示して起動する。Worker コードと不変なイメージ参照を同じリリースとして扱う根拠は [Cloudflare の Image Management](https://developers.cloudflare.com/containers/guides/image-management/) にある。既存の実行中 Run を新ジョブとして再送せず、従来の poll を継続する。移行前に永続化された実装依頼の本文は書き換えず、ハッシュを持たない旧ジョブでは従来の参照互換性を維持する。

32 KiB の最終ジョブ上限と、受理済み会話が増大した場合の `planning_input_too_large` は維持する。今回の変更は会話履歴を参照取得へ移すものではなく、Issue 本文の大きさに起因するジョブの増大を解消する。GitHub 読み取りの宛先・資格情報・実行モードは従来の制約を使う。
