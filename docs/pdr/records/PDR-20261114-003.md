# Issue の参照情報を JSON で渡し Agent が GitHub から本文を取得する

## 決定

PR #57 の後続で、GitHub Issue を起点とする計画・実装ジョブは、タイトル・本文を開始プロンプトに埋め込む方式から、構造化した `githubContext: { kind: "issue", number }` を Runner に渡す方式へ移行する。Agent は対象リポジトリに制限された `tailos_github_get` を自分で呼び、Issue のタイトル・本文を取得して作業する。

新しいラベル受付のプロンプトは固定の作業指示だけにする。計画ジョブは開始前の Issue スナップショットを D1 に保存し続けるが、Runner に渡す `planningContext` にはタイトル・本文を含めず、基準 SHA と受理済み会話を渡す。

対象 Issue の本文を取得しきらずに Agent が終了した場合は、成功扱いにせず既存の `agent_failed` とする。取得失敗は同じ実行中に再試行できる。ツールの既存の本文上限 16,000 UTF-16 単位を一回の取得量として維持し、`bodyOffset` / `nextBodyOffset` で残りを取得できるようにする。サロゲートペアは分割しない。対象 Issue は最初に取得した結果を実行中に保持し、ページ間で編集された本文を混在させない。

## 理由

Issue の内容をジョブへ事前展開すると、参照情報の追加が API のプロンプト構築やジョブのサイズ上限に結びつく。識別情報を渡して Agent が取得する方式は、参照対象を増やしやすく、長い Issue 本文も小さいジョブで扱える。取得したかどうかと全文の取得範囲を確認すると、参照漏れや先頭ページだけに基づく成功を防げる。

## 範囲と例外

[PDR-20261114-002](PDR-20261114-002.md) の移行を実施する判断である。[PDR-20261113-012](PDR-20261113-012.md) のうち Issue タイトル・本文を Agent に事前送信する部分には本記録を適用し、会話の受付順・保存・通知とモードの制約は維持する。受理済み会話は引き続き D1 を正とし、任意の GitHub コメントを自動で指示に取り込まない。Issue のタイトル・本文は自動編集しない。

API の保存する開始前スナップショットと、Agent の最初の取得時点の Issue は編集により異なりうる。Agent が使用するのは GitHub ツールの取得結果であり、診断が有効な場合はツールの入力・応答を既存の診断経路に記録する。開始前スナップショットを Agent の使用内容そのものとは扱わない。

`githubContext` は新しいジョブで使用する任意フィールドとし、これを持たない既存ジョブは従来どおり処理できるようにする。旧 Runner は新フィールドを受け付けないため、新 Runner イメージを利用可能にしてから新 API がジョブを送信する。移行前に永続化された実装依頼の本文は書き換えない。

32 KiB の最終ジョブ上限と、受理済み会話が増大した場合の `planning_input_too_large` は維持する。今回の変更は会話履歴を参照取得へ移すものではなく、Issue 本文の大きさに起因するジョブの増大を解消する。GitHub 読み取りの宛先・資格情報・実行モードは従来の制約を使う。
