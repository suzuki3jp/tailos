# Agent が Issue コメントを参照データとして取得する

## 決定

既存の GitHub 参照ツールに `kind: "issue_comments"` を追加する案を提案する。Run の対象リポジトリで Issue 番号を確認し、既存の GitHub App 読み取り権限で人と Bot のコメントを取得する。ID、投稿者名と種別、URL、作成・更新日時、本文を返す。

一覧は GitHub の順序で初回に 1 件を返し、続きがあれば継続値を返す。継続値が null なら終了とし、初回にコメントがなければ空の一覧を成功として返す。長文は既存の本文取得と同じ 16,000 UTF-16 コード単位を上限に分割し、サロゲートペアを保持する。コメントの全文を返してから次のコメントへ進む。

## 理由

コメントを明示的に取得できれば、Agent が必要なときに計画返信や議論を出所とともに参照できる。1 件ずつ返して既存の本文上限を再利用すると、コメント数と本文長の両方が大きい場合でも、一応答のサイズを抑えられる。受理済みの会話と参照データの信頼境界は [既存の取得方針](PDR-20261118-configurable-label-prompt.md) に従う。

## 範囲と例外

- 継続時は前回の位置のコメント ID を照合する。位置のずれを検出したら、初回からの取り直しを求める。分割した本文の継続ではコメント ID と本文ハッシュも照合し、編集を検出したらその本文を先頭から取り直す。
- 一覧は複数の GitHub リクエストにまたがる。位置照合は削除によるずれを検出するために使い、全コメントを一時点のスナップショットとして保証するものではない。取得済みコメントの後日の編集と、最終ページ確認後の投稿を確認するには初回から再取得する。全件の先読みや Run 内キャッシュは設けない。
- 認証失敗、対象外の番号、レート制限、タイムアウト、不正な応答は既存のツールエラー経路で返す。継続を確定できない場合も空の一覧として返さない。
- Codex と Claude の plan / implement から既存の読み取りツール経由で利用する。取得結果は出所付きの参照データとして扱う。受理済み指示への昇格、実行権限の追加、割り当て Issue 本文の取得完了判定、開始プロンプトへの自動展開はこの取得の作用に含めない。

## 選択肢と影響

複数件のメタデータを一覧で返し本文を個別取得する方式なら、多数のコメントから必要なものを選びやすい。1 件ずつ本文も返す案はツール契約を小さく保てる一方、コメント数に応じて API リクエストとツール呼び出しが増える。一覧全体を固定する方式は読み取り中の変更に強いが、全件を取得して保存する費用と保管上限の設計が必要になる。

## 未決事項

ツールの kind、1 回に返す件数、本文上限、一覧や本文の変更を検出したときの再開方法について合意を得てから実装する。
